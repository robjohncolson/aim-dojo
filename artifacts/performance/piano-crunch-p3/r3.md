# R3 — first-use piano construction and bounded shader warm

Implemented over R2 `5b80524`, preserving the earlier-bloom knobs and the accepted patch. `CFG.pianoFirstUse:0` restores the original path. The new path requires piano and LOW/crunch; legacy and HIGH retain their existing startup behavior.

After a valid activation and both native contexts running, `pianoWarmGraph` builds the existing drum graph and two sphere keys once. It preallocates 4 tick, 4 lead, 8 pad and 4 chord voices without attacking a note. This uses the same pinned Tone 14.8.49 borrow/return mechanism as existing `chorusWarm`, with cleanup in `finally` and retries after partial failure. It does not alter patches, note arguments, Transport, lookAhead or maxPolyphony (4/4/32/32).

Each warmed pool's existing idle GC interval is stopped once. This keeps the initial warm available for a late first hit; the memory tradeoff is retaining each pool's eventual high-water voices up to its original cap. It does not cap or shorten played notes. R1's oscillator ownership fix remains in place.

If PLAY arrives while either context is still resuming, `pianoWarmStartRun` waits before entering the run, with a three-second timeout and stale-completion token. This covers mobile/no-pointer-lock entry as well as desktop. It rechecks visibility, Temple, running state and modal/input blockers before continuing. Already unlocked starts continue synchronously; unavailable private prewarm APIs fall back to the original lazy behavior. No run clock is started during this wait.

`pianoWarmShadersStart` preserves representative creation order and prioritizes existing road, wall/arch, accent/veil, vault/dust, orb core/shell, target ring/drop, ribbon/arc loops, tether, shard and flash roots. Inverse mercy panes are descendants of the road/wall roots. Each compile retains the original lights and restores `scene.children` in `finally`. The finite critical queue survives PLAY in the existing 40 ms slices; remaining decorative/Temple work is discarded. A single synchronous driver call can exceed a slice budget. No shader, mesh appearance, GPU detector call, or PLAY-enable gate is changed.

Parked orb/shard/flash resources return to their pools before the first slice. Queue references still provide their material representatives, and PLAY can reuse the objects without another mesh/UUID allocation. The warm never later releases or hides an object that gameplay has acquired.
